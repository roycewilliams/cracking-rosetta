# What this repository has measured upstream to have wrong

GENERATED by `tools/upstream-findings.pl` on 2026-09-05 - do not edit; regenerate.

This page is for the people who maintain mdxfind, hashpipe and the hx
specification. It is not a complaint: almost everything in those documents
checks out, and the ones that do not were found precisely because this
repository refuses to record a mapping it has not reproduced. Each finding
below was measured here, and each says how.

Nothing on this page is asserted from reading. Where a finding names an entry,
the correction is carried by that entry with its proof, and this page renders
the entry's own note rather than a retelling of it - so if the entry is ever
re-seeded back to the published value, the page fails to build instead of
going quietly out of date.

**Two kinds of disagreement, and they live in different files.** A
disagreement that can be tested against a file vendored into this repository
is a record in `data/upstream-disagreements.yaml`, executed by
`tools/check-upstream.pl` on every build; those are summarized at the end. The
findings here are the ones that cannot be tested that way: an omission has
nothing to diff against, and an emission count needs the binary. Where a
finding *can* be executed it is paired with a record - Appendix A is vendored,
so a row stating the wrong construction is checked on every build, and the
record is what notices upstream fixing it. This page checks only that our own
side still makes the claim, which is why the pairing matters.

**How to read a `question`.** 0 of the findings below are measurements that disagree with a document and are *not* strong enough to overrule it. They are here so upstream can settle them from the source, and nothing in this repository has been withdrawn on the strength of them.

### MD5RAWUC (e383)

*A stated construction the type does not compute.* Measured 2026-09-02 with john 1.9.0-jumbo-1+bleeding-9a336d800a.

| | |
|---|---|
| the document states | `hex(upper(md5_bin(pass)))` |
| measured here | `md5(upper(md5(md5_raw($p))))` |

The row applies upper() to RAW BYTES and hexes the result afterwards, which is not the same operation as upper-casing the hex text and is not what the type does. The entry carrying this type reaches tier vector with the upper() outside the hex-emitting call, proven by john's own dynamic compiler against the entry's own vector. Note that the entry is at -i 2, so its expression carries one more round than the row describes; the defect being reported is the placement of upper(), which is independent of the iteration count.

### PEOPLESOFT (e858)

*A stated construction the type does not compute.* Measured 2026-09-02 with mdxfind source RCS 1.545 (2026/08/29).

| | |
|---|---|
| the document states | `sha1(utf16be(upper(pass)))` |
| measured here | `base64(sha1_raw(utf16le($p)))` |

Two errors in one row. The row states the big-endian widening and a case fold; mdxfind.c's JOB_PEOPLESOFT converts the candidate through an iconv descriptor opened UTF-8 to UTF-16LE//IGNORE and folds no case at all, then base64-encodes the raw 20-byte digest rather than hexing it. Corroborated four further ways, all independent of each other: mdxfind's own hx VM built standalone from the same tree, a recomputation in Perl, hashcat -m 133, and john's dynamic compiler.

## hx specification, Note [24]

### MD5BASE64SHA1RAW (e238), MD5UCBASE64SHA1RAW (e376)

*A stated construction the type does not compute.* Measured 2026-09-05 with mdxfind.c, the JOB_MD5BASE64SHA1RAW case.

| | |
|---|---|
| the document states | both emit the full-length base64 string and a 2-character-shorter variant |
| measured here | one emission each; there is no shorter variant to take |

Note [24] groups these two with e237 MD5BASE64MD5RAW and e375 MD5UCBASE64MD5RAW as emitting both the full base64 string and a two-character-shorter variant. mdxfind has two code paths and only one does that: b64md5raw computes a second digest over len-2, b64sha1raw sets x = 1 and goes straight to MDstart. The difference is arithmetic rather than an oversight in the code -- an md5 digest is 16 bytes and its base64 ends in two "=" characters, while a sha1 digest is 20 and its base64 ends in one, so for the SHA1RAW pair there is no two-character variant to take. Narrowed here from six types to two on 2026-09-05: the other four -- SHA1MD5BASE641SALT, SHA1MD6TRUNC, SHA1SALTSHA256UCTRUNC and SHA1SALTSHA512UCTRUNC -- are multi-emit in the source, so the note was right about them and the earlier measurement was wrong.

The 2 type(s), as the binary spells them:

`MD5BASE64SHA1RAW`, `MD5UCBASE64SHA1RAW`

## How to report a mistake in this page

Open an issue. A finding here is only worth having if it is right, and the
fastest way to retire one is to show the measurement that contradicts it - the
invocation, the version, and what came back. This repository has been wrong in
both directions and re-run things on the strength of one message, so a
correction is welcome rather than merely tolerated.

A finding that upstream has fixed should be deleted here rather than left
standing with a note, for the same reason a converged record is deleted from
`data/upstream-disagreements.yaml`: a page of retired findings is a page
nobody trusts the current ones on.
