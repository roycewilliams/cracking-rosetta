# What this repository has measured upstream to have wrong

GENERATED by `tools/upstream-findings.pl` on 2026-09-04 - do not edit; regenerate.

This page is for the people who maintain mdxfind, hashpipe and the hx
specification. It is not a complaint: almost everything in those documents
checks out, and the ones that do not were found precisely because this
repository refuses to record a mapping it has not reproduced. Each finding
below was measured here, and each says how.

Nothing on this page is asserted from reading. Where a finding names an entry,
the correction is carried by that entry with its proof, and this page renders
the entry's own note rather than a retelling of it - so if the entry is ever
re-seeded back to the published value, the page fails to build instead of
going quietly out of date.

**Two kinds of disagreement, and they live in different files.** A
disagreement that can be tested against a file vendored into this repository
is a record in `data/upstream-disagreements.yaml`, executed by
`tools/check-upstream.pl` on every build; those are summarized at the end. The
findings here are the ones that cannot be tested that way: an omission has
nothing to diff against, and an emission count needs the binary. Where a
finding *can* be executed it is paired with a record - Appendix A is vendored,
so a row stating the wrong construction is checked on every build, and the
record is what notices upstream fixing it. This page checks only that our own
side still makes the claim, which is why the pairing matters.

**How to read a `question`.** 2 of the findings below are measurements that disagree with a document and are *not* strong enough to overrule it. They are here so upstream can settle them from the source, and nothing in this repository has been withdrawn on the strength of them.

### MD5RAWUC (e383)

*A stated construction the type does not compute.* Measured 2026-09-02 with john 1.9.0-jumbo-1+bleeding-9a336d800a.

| | |
|---|---|
| the document states | `hex(upper(md5_bin(pass)))` |
| measured here | `md5(upper(md5(md5_raw($p))))` |

The row applies upper() to RAW BYTES and hexes the result afterwards, which is not the same operation as upper-casing the hex text and is not what the type does. The entry carrying this type reaches tier vector with the upper() outside the hex-emitting call, proven by john's own dynamic compiler against the entry's own vector. ### PEOPLESOFT (e858)

*A stated construction the type does not compute.* Measured 2026-09-02 with mdxfind source RCS 1.545 (2026/08/29).

| | |
|---|---|
| the document states | `sha1(utf16be(upper(pass)))` |
| measured here | `base64(sha1_raw(utf16le($p)))` |

Two errors in one row. The row states the big-endian widening and a case fold; mdxfind.c's JOB_PEOPLESOFT converts the candidate through an iconv descriptor opened UTF-8 to UTF-16LE//IGNORE and folds no case at all, then base64-encodes the raw 20-byte digest rather than hexing it. Corroborated four further ways, all independent of each other: mdxfind's own hx VM built standalone from the same tree, a recomputation in Perl, hashcat -m 133, and john's dynamic compiler.

The evidence, as it stands in `data/algorithms/peoplesoft.yaml` under `expression_proof.note`:

## hx specification, Note [24]

Nothing was withdrawn on these and nothing should be. A measured 1 is not a refutation: several families take extra input -- a -u user list, a -j pepper array, a salt file -- that a plain -z invocation does not supply, and NTLM is the standing example of a type that prints one under -z while hx Note [29] states it emits three. ### 11 multi-emit types the note does not name

*Something the document does not say.* Measured 2026-09-02 with mdxfind source RCS 1.545 (2026/08/29); mdxfind -z.

| | |
|---|---|
| the document states | 34 types emit several candidate digests per input |
| measured here | at least 11 more do, by running the same C |

Note [24] names the types that sit AT a C case label whose body emits several digests. It does not name the types that reach that same body by falling through from an earlier label or by jumping into it, although they run exactly the same code and therefore emit exactly as many. The clearest case is mdxfind.c's b64md5raw block, which md5s the base64 of a raw digest and then md5s the same string minus its "==" padding, and checks both: MD5BASE64MD5RAWMD5 falls into it and MD5BASE64MD5RAWSHA1 jumps to it, and the note names neither. Each type listed here was confirmed twice over -- the source says the body emits more than one, and mdxfind -z agrees -- because a single expression for a multi-emit type is a false claim even when the string is one of the forms.

The 11 type(s), as the binary spells them:

`MD5BASE64MD5RAWSHA1`, `MD5BASE64MD5RAWMD5MD5`, `MD5BASE64MD5RAWMD5`, `MD5-DBL-PASS`, `SHA1MD5MD5PASS`, `MD5SQL5-32`, `SHA1SQL5`, `SHA1SQL5MD5`, `SHA1SQL5MD5MD5`, `MD52SALTMD5MD5`, `MD52SALTMD5MD5MD5`

## vendored hashpipe HASH_TYPES.md

### types whose example digest is rendered in upper-case hex

*An example the tool will not read back.* Measured 2026-08-31 with mdxfind RCS 1.545 (2026/08/29).

| | |
|---|---|
| the document states | the example is the complete self-test vector, in the format the tool accepts |
| measured here | mdxfind's loader will not read those examples back |

The catalog says every example passes its self-test and is in the format the tool accepts as input. For these types the digest is printed in upper-case hex, and feeding one back is not a round-trip -- it is a hash the loader declines. Re-casing is not a general fix and must not be treated as one: of the types this repository has chased, only MD5UCBASE64SHA1RAW turned out to be purely a case problem, while MD5UC, SHA256UC and RACF reproduce in neither case, so something else is wrong with those rows as well. Re-casing on failure is a search for a string that passes rather than a fix, which is why this is reported rather than patched locally. SHA256UC is now measured further, 2026-09-04, and the result narrows the bug rather than widening it: the published digest IS sha256 of the published plaintext. Lower-cased and offered to mdxfind's own SHA256 type it reproduces at once, as SHA256x01, so the DIGEST in the catalog is correct and it is the SHA256UC type that cannot read its own example in either case. hashpipe verifies the same line under -c pinned to SHA256UC, so the two tools disagree about that type and not about the hash.

## How to report a mistake in this page

Open an issue. A finding here is only worth having if it is right, and the
fastest way to retire one is to show the measurement that contradicts it - the
invocation, the version, and what came back. This repository has been wrong in
both directions and re-run things on the strength of one message, so a
correction is welcome rather than merely tolerated.

A finding that upstream has fixed should be deleted here rather than left
standing with a note, for the same reason a converged record is deleted from
`data/upstream-disagreements.yaml`: a page of retired findings is a page
nobody trusts the current ones on.
