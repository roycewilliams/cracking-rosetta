# cracking-rosetta

A cross-reference of password-cracking algorithm identifiers across [hashcat](https://hashcat.net/hashcat/), [John the Ripper](https://www.openwall.com/john/), [mdxfind](https://github.com/Cynosureprime/mdxfind) / [hashpipe](https://github.com/Cynosureprime/hashpipe), and - historical only - Alec Muffett's [Crack](docs/CRACK.md). <!-- counter --> 1571 <!-- endcounter --> algorithms, one YAML file each.

You have a hashcat mode 2811 hash. What does John call it, and can mdxfind do it?

```yaml
tools:
  hashcat:  { modes: [2811],               verified: vector }
  john:     { cpu: [dynamic_12],           verified: upstream }
  mdxfind:  { types: [MD5-MD5SALTMD5PASS], verified: vector }
```

It continues the community "rosetta stone" spreadsheet, which had drifted far behind its upstreams.

## Look something up

Same data, four formats. Pick the one that fits how you work:

| Where | For |
|---|---|
| [`docs/index.html`](docs/index.html) | searching and filtering in a browser |
| [`docs/ROSETTA.md`](docs/ROSETTA.md) | reading one flat table |
| [`dist/rosetta.csv`](dist/rosetta.csv) | the spreadsheet equivalent: one row per algorithm, one column per tool |
| [`dist/rosetta.json`](dist/rosetta.json) | scripting |

Every algorithm has a stable `id` such as `md5-pass-salt`. It keys the CSV, names the file under `data/algorithms/`, and is the fragment on the browsable page, so `index.html#md5-pass-salt` is a permalink you can paste into an issue.

## How well a mapping is known

A cross-reference rots silently: a row that was right in 2021 still looks right after upstream renames a format or changes its salt handling, and a spreadsheet cell never says whether anyone checked. So every mapping carries a tier.

| Tier | Meaning |
|---|---|
| `vector` | this repo cracked the entry's own test vector with that tool, under that exact identifier. **Proven.** |
| `upstream` | asserted by a project that verifies by recomputation (mdxfind's type table, hashpipe's `john_map.h`) |
| `asserted` | a human said so; no reproduction on record |
| `absent` | that tool does not support this algorithm |

The tier is per tool, in the CSV's `*_state` columns. **If you automate against this, filter to `vector`**: 933 mappings across 653 entries. A failed round-trip never demotes a mapping, because a vector that won't crack may mean a wrong mapping, a wrong plaintext, or a missing salt, and the exit status can't tell them apart.

## Scripting against it

Promises for anyone consuming the exports:

- **An `id` never changes** - filename stem, CSV key, URL fragment. A merge turns the losing id into a *tombstone* (`status: merged`, `merged_into` names the survivor, other columns empty), so an old id keeps resolving and tells you where the row went.
- **Read the CSV by header name, not column position.** Columns get added anywhere in the row; nothing is renamed or removed without a note here.
- **The four tiers are the fixed vocabulary** (`vector`, `upstream`, `asserted`, `absent`). What changes is which one a mapping has earned.
- **`docs/` and `dist/` are generated** on every change. Don't edit or PR them. The two hand-written exceptions say so in their first line: [`docs/CRACK.md`](docs/CRACK.md) and [`docs/OTHER-TOOLS.md`](docs/OTHER-TOOLS.md). The test is the `GENERATED by` header, not the directory.
- **`data/tools/*.yaml` is upstream's own output**, regenerated wholesale on upgrade. This repo tracks each tool's upstream *tip*, not its releases - the mappings people arrive asking about are the new ones - so an inventory routinely names identifiers a release build lacks.
- **[`dist/availability.csv`](dist/availability.csv) is how you check that against your build**: one row per (tool, identifier) with the earliest upstream version carrying it. Read `first_version` with `first_version_exact` beside it (`no` means it was already present in the oldest version the derivation sees, so it may be older); an empty `first_version` means no tagged release has it yet. As of 2026-09-15, 9 of 596 hashcat modes and 53 of 402 John formats are in no release at all. John's 150 `dynamic_N` labels aren't covered, being config-defined rather than a C literal. It tells you whether your build *recognizes* an identifier, not whether it computes it correctly. It is generated locally (it needs upstream clones), so `validate.pl` flags when it drifts from the inventories.

Columns whose meaning isn't obvious:

- **`suites_proven` / `suites_decided`** - the sortable "who agrees?", two integers from 0 to 3. `proven` counts suites that round-tripped a vector under an identifier this row publishes; `decided` counts suites that answered at all (a proven absence or an unreproduced claim is decided but not proven). Sort `suites_proven` descending, then `suites_decided`. There are **three** suites, not four: mdxfind and hashpipe are one project read by two instruments and count once, and Crack is frozen. A finished row can be `proven` 1, `decided` 3 - every suite answered and two genuinely can't do it (613 rows).
- **`<tool>_match`** - what was conceded to earn the tier; absent when the round trip was byte-exact (the usual case). Values: `plaintext-case` (the tool returns a case-only variant, by construction), `plaintext-reserialized` (the tool echoes a re-encoded plaintext), `hash-transcoded` (the round trip used the type's own spelling from `data/mdxfind-transcodes.tsv`). A truncating match is deliberately not here: it earns a `truncates` relation and no mapping.
- **`expression` vs `john_dynamic_expr`** - `expression` is hx notation, which spells a representation change as a wrapper: `md5(upper(md5($p)))`. John spells it as a flavor of the hash function, `md5(MD5($p))`, and rejects the wrapper form. So `john_dynamic_expr` is the string to paste after `john --format=`; where the two differ they are one claim written twice.
- **`serialization`** - whether the tools agree on the *string*. `shared`: one vector here loaded in every tool that reads anything on the row, so a hash in that form is portable. `divergent`: no single string does (hashcat writes Kerberos AS-REP with the checksum early, John wants it last). `unknown`: fewer than two tools have read anything here (most rows).
- **`form` / `primary_form`** - each vector's `form` is `native` (the shape the producing system stores) or a tool name (that tool's spelling). The native vector is primary; `primary_form` says whether the row has one. `native` is only ever set by a person who knows the system.
- **`hashcat_salted`, `john_salted`, `mdxfind_salted`, `hashcat_speed`, `john_work_factor`** - read straight from the inventories, so they can't drift from the tool, but each is a fact about *one tool's mode*, not the algorithm: bcrypt is `hashcat_salted: yes` and `mdxfind_salted: no`. There is no merged `salted` column, and `mixed` means a row's own identifiers for that tool disagree. These are lookups, not tiered claims.
- **`hash_length` / `hash_length_basis`** - length of the leading hex field. `fixed` (vectors agree), `observed` (a single vector; most rows), `varies` (vectors disagree, both lengths given - `lm` is 16 or 32). Empty for container formats. `nesting_depth` counts hash applications, not brackets: `md5(upper(md5($p)))` is 2.
- **`reads_in` / `credential`** (per vector, in `data/algorithms/`) - `reads_in` lists the tools measured to read that exact string (every tool is tried against every vector, so absence means it declined). `credential` is the stronger, human-set claim that two strings are one credential written twice.

No benchmarked speed is published: it would be a fact about one host's GPU and build and would rot the day either changed. hashcat's own `slow` flag gives the distinction you plan around.

## Verifying and contributing

The source of truth is one YAML file per algorithm under `data/algorithms/`; `docs/` and `dist/` are generated from it. Correct a mapping there, not in a generated cell.

Regenerate a tool's inventory (only needed when the tool is updated):

```
tools/extract-hashcat.pl --binary /usr/local/bin/hashcat   > data/tools/hashcat.yaml
tools/extract-john.pl    --binary .../john-latest/run/john > data/tools/john.yaml
tools/extract-mdxfind.pl --binary /usr/local/bin/mdxfind \
    --catalog vendor/cynosureprime/hashpipe-HASH_TYPES.md  > data/tools/mdxfind.yaml
```

Each takes `--from FILE` (or `stdin`) to diff captured output without the binary present.

Check and prove a change:

```
tools/fmt.pl --all           # canonical YAML; also catches a misspelled key
tools/validate.pl --changed  # errors only in entries you touched (CI runs it over everything)
tools/review-delta.pl        # what your change actually claims
tools/verify-vectors.pl --tool all   # round-trip; needs the tools installed, GPU for hashcat
```

`validate.pl` resolves every identifier you name against the inventories: whether mode 2811 exists in *this* hashcat, whether `dynamic_12` is really a CPU format. Naming an identifier no tool has is the likeliest defect here, and what the spreadsheet accumulated over three years. The verifiers honor `$JOHN` / `$HASHCAT` / `$MDXFIND`, then the paths this data came from, then `PATH`; `--john` / `--hashcat` / `--mdxfind` override.

PRs are welcome for the data, the extractors, the validator, the CI. Three rules:

- **Don't hand-edit `data/tools/` or `vendor/`.** Both are generated and carry a `GENERATED` banner. Re-run the extractor, or refresh `vendor/` with `tools/fetch-upstream.sh` and commit it separately.
- **Don't inflate tiers.** `vector` means this repo cracked the vector, not "I'm confident". An honest `asserted` with a `note` saying where the claim came from beats a hopeful `vector`.
- **If your source contradicts an entry, add your claim in `note`** rather than overwriting it. Disagreements get settled by verification.

Keep PR descriptions and comments lean: say what changed and why, and stop.

Full procedures: [CONTRIBUTING.md](CONTRIBUTING.md) to add or correct, [MAINTAINING.md](MAINTAINING.md) to review.

### Where to help

All four lists are generated from the data:

- [`docs/GAPS.md`](docs/GAPS.md) - what's missing, ranked by cost to fix: believed-but-never-reproduced mappings (one command settles them), then entries that need only a test vector (no cracker required).
- [`docs/OPEN-QUESTIONS.md`](docs/OPEN-QUESTIONS.md) - rows that need a person, not a command: an expression John states but can't reproduce, a tool that cracks a vector without implementing the algorithm, an entry that may be two algorithms in one row.
- [`docs/UPSTREAM-FINDINGS.md`](docs/UPSTREAM-FINDINGS.md) - where verifying a mapping turned up something a published document gets wrong. Each names the version measured and is re-checked every build, so a finding upstream has already fixed fails the build rather than lingering.
- [`docs/OTHER-TOOLS.md`](docs/OTHER-TOOLS.md) - why a given tool is or isn't a column.

## Layout

```
data/algorithms/*.yaml   curated, one file per algorithm - the PR surface
data/tools/*.yaml        generated inventories - never hand-edited
data/upstream-disagreements.yaml   where we knowingly differ from a vendored
                         catalog, executed by tools/check-upstream.pl
data/mdxfind-transcodes.tsv   a vector in an mdxfind type's own serialization,
                         where the stored form can't be read back
schema/                  entry shape, for editors and consumers
tools/                   extractors, validator, verifier, review helpers
vendor/cynosureprime/    vendored upstream catalogs, with provenance
```

Inventory (what a tool supports) is kept apart from mapping (which identifiers mean the same thing), so a new hashcat release regenerates one layer without touching the other. One file per algorithm, not one table: you touch one small file, merge conflicts vanish, `git blame` is per-algorithm, and CODEOWNERS can route by path.

### Regression corpus for mdxfind

[`dist/mdxfind-corpus.tsv`](dist/mdxfind-corpus.tsv) is this repo's proven vectors in mdxfind's own serialization - one row per (type, vector) with the type name, `eN` index, iteration count, reader flag, pepper, hash line, and expected plaintext. Every row was reproduced by driving the binary, not transcribed (`tools/mdxfind-corpus.pl --export`); `--check` re-runs the file and names anything that stopped reproducing. Beyond the vectors it records what a catalog doesn't: which reader flag each type needs, which pepper types want the salt field split, and one hash length per run (mdxfind compares at the shortest hash it loaded and will happily match a truncation).

## Practical notes

- **mdxfind's iteration count is part of the identity.** `MD5` at `-i 2` is `md5(md5($pass))`, which is John's `dynamic_2`, not `dynamic_0`. The spreadsheet lost these; 17 were recovered from mdxfind's output suffix.
- **mdxfind's hashcat column lists *related* modes, not equivalents.** Type `MD5` names modes 0, 2600, 3500 and 5100 - four algorithms it reaches by varying `-i` and truncation. Only the 279 one-to-one mappings were seeded; the other 18 are left for a human.
- **Crack is not a column.** It attacks two of these algorithms; those two are marked (c) and the detail is in [docs/CRACK.md](docs/CRACK.md). `tools.crack` is still in the data and both exports.
- **A missing tool column is an open question, not a claim of absence.** `absent` is a claim, and it is stated explicitly.
- **John's case varies** - `Raw-MD5` on CPU, `raw-MD5-opencl` on GPU. Use the exact label the inventory lists.
- Some John dynamics are switched off by the stock `dynamic_disabled.conf`. They're real formats and valid to reference; `john.yaml` records them separately so this data doesn't depend on one host's config.
- `algorithm_name` in `john.yaml` reports the kernel *this* host built, SIMD width and all, so compare labels and example ciphertexts rather than that field when hunting for drift.
- Several ids are still things like `md5-md5-plain-salt-3`, the spreadsheet's names. Renaming an id breaks anyone automating against it, so they stay.
- Coverage is partial and visibly so; run `tools/validate.pl` for live numbers. As of 2026-08-29 the inventories held 593 hashcat modes, 552 John formats, and 1001 mdxfind types.

## Credits

The verified seed data is [Cynosure Prime](https://github.com/Cynosureprime)'s: mdxfind ships a hashcat mapping for 298 of its types, and hashpipe's `john_map.h` maps 125 John dynamic formats to mdxfind types, each confirmed by recomputation across 9672 harvested vectors, with the rows that wouldn't verify omitted rather than guessed. That practice is the model this repo follows.

[Waffle2](https://github.com/Waffle2), who writes mdxfind and hashpipe, has contributed directly. PR #1 (merged 2026-09-04) brought the mdxfind inventory to 1027 types and marked three that can't carry a vector. PR #8 (merged 2026-09-16) re-measured 91 rows against the four engines, corrected the HMAC keying (John's `HMAC-SHA1` and mdxfind's `HMAC-SHA1` are precisely the two identifiers that do *not* correspond), added 49 hashpipe mappings, and brought the denotation and vector-width audits. Being upstream of two of the four tools, he can say what a type computes and when it changed - and his claims still get round-tripped locally like anyone else's.

The rest came from the spreadsheet, started 31 March 2018 and built up over the years by many [HashMob](https://hashmob.net/) members working real lists. The tiers are not a verdict on that work; they record what has been re-checked since, and most of what has been re-checked has held.
